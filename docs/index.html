What it is and why

Three parts, one job: Bangla dictation that stays in Bangla.

Gboard's on-device voice cleanup tends to rewrite Bengali dictation into Latin letters and mangles sentences that mix Bangla and English. Rambler Bangla fixes this for one exact build, Gboard 18.3.1: a fail-closed smali patcher (Python) proves it is looking at the profiled build and inserts two hooks, a pure-Java policy runtime keeps Bangla in Bengali script and picks one language per sentence, and a device-free CI suite builds a synthetic APK, patches it and checks every step, refusals included, on every push.

Honest status. A maintainer project with private test builds. Host tests and a static CI suite back the engineering claims. On-device results come from the maintainer's own phone. "Design intent" means design, not proof. CI never installs the keyboard on a device.

How it works

The patcher never edits bytes by offset. It disassembles the APK and patches only once every check has passed.

  1. Fingerprint guard

    Every SHA-256 string hash in the profile must be found, both method anchors must match exactly, and the enabled-languages register is found by tracing dataflow.

  2. Smali patch

    Two hook calls go into the cleanup builder. The stock rule string stays as the fail-safe input. Only the touched DEX is rebuilt.

  3. Policy runtime

    Pure-Java String to String rules, dexed with d8 and added as an extra DEX. No Android or network dependencies.

  4. Verify

    scripts/verify_apk.sh checks the output offline. The patcher never signs: you re-sign with your own key.

Any miss at step 1: FAIL-CLOSED ABORT, exit status 2, no output written. Full design in ARCHITECTURE.md.

Device-free CI

No phone, emulator or Google binary needed to prove the pipeline.

The fixture is a synthetic APK with zero Google content that mirrors the real anchors. On every push and pull request, GitHub Actions builds it from smali sources, patches it with the real patcher and asserts on the result.

  • Python unit tests (stdlib only): the patcher's pure helpers, the loanword table sync, and checks that keep the README and this page honest.
  • Static suite, 17 checks: 51 policy assertions, fixture build, end-to-end patch, fail-closed negatives (wrong fingerprint, tampered rule, re-patch each exit 2 with no APK), APK Signature Scheme v2 verification.

CI does not prove runtime behaviour inside real Gboard. Phone evidence is dated in VALIDATION.md.

Build from source

Linux x86_64, JDK 17+ (CI uses Temurin 21), Python 3, curl, unzip and zip. Target: Gboard 18.3.1.977415014 beta, version code 176004238, arm64-v8a. Any other build is refused.

# tests, then the pinned toolchain (SHA-256 checked)
python3 -m unittest discover -s tests/python -v
python3 -m pip install androguard==4.1.4
bash scripts/bootstrap_tools.sh && source tools/tool-env.sh
bash tests/run_tests.sh   # TEST SUITE: 17 passed, 0 failed

# 1. fingerprint guard
python3 standalone-patcher/dex_patch.py analyze \
  --apk gboard-18.3.1.apk --profile fingerprints/gboard-18.3.1.json
# 2-3. smali patch + policy runtime (exit 2, no output, on any miss)
python3 standalone-patcher/dex_patch.py patch \
  --apk gboard-18.3.1.apk --out out.apk \
  --profile fingerprints/gboard-18.3.1.json --extension-dex build/ext-dex/classes.dex
# 4. verify offline
scripts/verify_apk.sh single out.apk --profile fingerprints/gboard-18.3.1.json

Safety: fail-closed by design

The patcher would rather do nothing than guess.

  • Exact build or nothing. Any fingerprint, anchor or dataflow miss exits 2 and writes no APK.
  • No double patching. An already patched APK is refused.
  • Hash-only profile. No Google strings are reproduced.
  • Never signs, never uploads. Patcher and verifier run offline; you sign with your own key.
  • No network code in the patch layer, and diagnostics are off by default and stay on your phone.
  • On-device path only. Bangla is not on Google's cloud rewrite list, so only the on-device cleanup path changes.

FAQ

Can I download a ready-made APK?

No. The project is source only; see above.

Why only Gboard 18.3.1?

The hooks go into obfuscated code whose names change between builds. Pinning one build and proving it with fingerprints is what makes the patch safe. A new version needs a new, reviewed profile.

What happens with a different version?

It refuses: FAIL-CLOSED ABORT, exit status 2, no output. Nothing is half-patched.

Does CI prove it works on my phone?

No. CI proves the patching pipeline on a synthetic APK, refusals included. Phone results come from the maintainer's device and are labelled as such.

Does it send my voice or text anywhere?

The patch layer has no network code. It only rewrites prompt and rule strings inside Gboard's existing on-device cleanup step. Gboard's own behaviour is outside this project's audit.

Does it translate English into Bangla?

No. English words spoken inside Bangla get a Bangla spelling; they are never translated.

Why do I need Linux?

The pinned aapt2 used to build the test fixture is the Linux build. The patcher itself is plain Python.

Bangla still came out in Latin letters. Is that Rambler?

Turn off Bangla script correction and try again. Same result means it is Gboard's own output. Otherwise, please open an issue with the layout you used.
